02Basics: Days 1 to 4

Install, context, prompts and plan mode. 6 questions.

Q1 What is the loop from Day 1 that works for a one-line fix and for a whole feature?

  1. Ask, retry, retry, accept
  2. Plan, build, deploy, monitor
  3. Explore, plan, build, verify
  4. Prompt, accept, commit, push
Show the answer

Answer: C. Explore, plan, build, verify

What. Explore (read the code and explain it back), plan (agree the steps), build (in small steps), verify (run tests, read the diff). Why. Each step catches a different kind of mistake before it gets expensive. How. Start every task with "read how X works, change nothing", then ask for a plan before any edit.

Covered on Day 1.

Q2 Which of these belongs in your CLAUDE.md?

  1. Commands to test and lint, team conventions, and things to avoid
  2. Your API keys, so it can call the service
  3. A diary of what you changed each day
  4. The full source of your main file, so it has it handy
Show the answer

Answer: A. Commands to test and lint, team conventions, and things to avoid

What. CLAUDE.md is a short briefing that loads at the start of every session: commands, conventions and mistakes to avoid. Why. Every line costs context, and a long file gets ignored. Secrets never belong in it, because it is committed to git. How. Run /init in the terminal or the VS Code panel, then trim the draft. If Claude gets something wrong twice, add a line.

Covered on Day 2.

Q3 You installed the Claude Code VS Code extension. Typing claude in VS Code's integrated terminal says command not found. Why?

  1. The extension is broken and must be reinstalled
  2. The extension bundles its own copy for the chat panel but does not add claude to your PATH
  3. VS Code blocks terminal commands by default
  4. You need an API key first
Show the answer

Answer: B. The extension bundles its own copy for the chat panel but does not add claude to your PATH

What. The panel and the command-line tool are two doors to the same engine, but only the standalone install puts claude on your PATH. Why it matters. Commands such as claude mcp add and claude -p need the CLI. How. Run the native installer once (irm https://claude.ai/install.ps1 | iex on Windows PowerShell, curl -fsSL https://claude.ai/install.sh | bash on macOS, Linux and WSL), then open a new terminal and check claude --version.

Covered on Day 3.

Q4 Claude is heading down the wrong path mid-task. What is the best move?

  1. Type /clear and start over
  2. Press Esc straight away and tell it what you want instead
  3. Wait for it to finish, then undo everything
  4. Close the terminal
Show the answer

Answer: B. Press Esc straight away and tell it what you want instead

What. Esc stops Claude mid-turn and keeps the work so far. Why. Every extra step on a bad path costs time and tokens, and its dead ends stay in the context. How. In the terminal press Esc; in VS Code use the stop button. Then say what to do instead. Esc twice (or /rewind) goes back to an earlier checkpoint.

Covered on Day 4.

Q5 When is plan mode worth the extra step?

  1. Never, it only slows you down
  2. When the change touches several files, the code is unfamiliar, or you cannot describe the diff in one sentence
  3. Always, even for a typo
  4. Only on Mondays
Show the answer

Answer: B. When the change touches several files, the code is unfamiliar, or you cannot describe the diff in one sentence

What. In plan mode Claude reads and proposes but cannot edit until you approve. Why. Reading a plan takes a minute; undoing the wrong build takes an afternoon. A one-line rename does not need it. How. Terminal: claude --permission-mode plan, /plan or Shift+Tab. VS Code: pick Plan from the mode indicator under the prompt box.

Covered on Day 4.

Q6 What does /rewind NOT undo?

  1. Side effects of shell commands, such as deleting files with rm or changing a database
  2. Messages in the conversation
  3. A change you rejected
  4. Edits Claude made to your files
Show the answer

Answer: A. Side effects of shell commands, such as deleting files with rm or changing a database

What. /rewind restores the code edits Claude made with its own edit tools, the conversation, or both. Why it matters. It does not track changes made by shell commands or outside the session, so it is a quick undo, not a backup. How. Keep using git as the permanent safety net (Day 6): commit before big tasks.

Covered on Day 4.

03Control: Days 5 and 6

Context, permissions, git and reviews. 6 questions.

Q7 The task has changed completely (from a bug fix to a new feature). Which command fits?

  1. /diff
  2. /context
  3. /clear
  4. /compact
Show the answer

Answer: C. /clear

What. /clear starts a new conversation with an empty context; /compact summarises the current one. Why. Old, unrelated chat clutters the context and is sent again with every request. How. /compact (with a line on what to keep) when it is the same task but long; /clear when the task changed. Use /rename first if you want to find the old session later.

Covered on Day 5.

Q8 You have allow: Bash(git *) and deny: Bash(git push *). What happens when Claude tries git push?

  1. Whichever rule was written last wins
  2. It is blocked, because deny is checked first
  3. It asks you every time
  4. It is allowed, because allow is broader
Show the answer

Answer: B. It is blocked, because deny is checked first

What. Rules are evaluated in order: deny, then ask, then allow, and the first match decides. Why. An allow rule can never carve an exception out of a deny rule, so a deny is a dependable fence. How. Open /permissions in the terminal or VS Code panel to see and edit the rules. Note that Bash(git *) allows every git command including push, while Bash(git log *) allows only git log.

Covered on Day 5.

Q9 Which settings file is committed to git, so the whole team gets its permission rules?

  1. CLAUDE.md
  2. .claude/settings.local.json
  3. ~/.claude/settings.json
  4. .claude/settings.json in the project
Show the answer

Answer: D. .claude/settings.json in the project

What. Rules live in three places: .claude/settings.local.json (yours, not committed), .claude/settings.json (shared, committed) and ~/.claude/settings.json (all your projects). Why. Shared rules give a team one safe setup without a wiki page. How. Put team rules in the project file and review changes to it in a pull request like code.

Covered on Day 5.

Q10 Your CLAUDE.md says "never touch the .env file". What actually guarantees Claude cannot read it?

  1. Nothing, the sentence is enough
  2. Asking nicely twice
  3. Writing it in capital letters
  4. A deny rule such as Read(./.env) in settings
Show the answer

Answer: D. A deny rule such as Read(./.env) in settings

What. CLAUDE.md shapes what Claude tries; permission rules are enforced by Claude Code itself. Why. An instruction can be forgotten or misread, a deny rule cannot. How. Add "deny": [ "Read(./.env)" ] under permissions in .claude/settings.json. For rules that must run every time, Day 9 adds hooks.

Covered on Day 5.

Q11 Before asking teammates to review your branch, what is a quick first check you can run?

  1. /init
  2. /model
  3. /rename
  4. /code-review (alias /review) on your current changes
Show the answer

Answer: D. /code-review (alias /review) on your current changes

What. /code-review reviews the current diff for bugs; pass a PR number or branch, or a level such as high. Why. It catches the obvious problems before a human spends time. Treat each finding as a lead to check, not an order. How. Terminal or VS Code panel: type /code-review. Also try /security-review on a branch.

Covered on Day 6.

Q12 Which pair of git commands is most worth putting in your deny list?

  1. git add and git commit
  2. git status and git diff
  3. git push --force and git reset --hard
  4. git log and git show
Show the answer

Answer: C. git push --force and git reset --hard

What. Force-push and hard reset are the two commands that destroy work. Why. Read-only git (status, diff, log) is safe to allow; commit and push are worth a look, so leave them on ask. How. "deny": [ "Bash(git push --force *)", "Bash(git reset --hard *)" ] in .claude/settings.json. Also work on a branch, never on main.

Covered on Day 6.

04Extend: Days 7 to 10

MCP, skills, subagents, hooks and plugins. 7 questions.

Q13 Where does a team-shared MCP server configuration live, and how should its token be stored?

  1. In your clipboard
  2. In CLAUDE.md, with the token typed in
  3. In .mcp.json, with the token typed in
  4. In .mcp.json at the project root, with the token as an environment variable like ${API_KEY}
Show the answer

Answer: D. In .mcp.json at the project root, with the token as an environment variable like ${API_KEY}

What. Project scope stores servers in .mcp.json, which you commit (add with --scope project). Why. A committed file is visible to everyone with the repo, so a pasted token is a leaked token. How. Write "Authorization": "Bearer ${API_KEY}"; each person sets the variable on their own machine. Teammates are asked to approve the server the first time they open the project.

Covered on Day 7.

Q14 With MCP, who decides which tool to call and when?

  1. The MCP server
  2. The operating system
  3. Anthropic's servers
  4. Claude, based on the tool descriptions the server lists
Show the answer

Answer: D. Claude, based on the tool descriptions the server lists

What. A server only lists tools and runs them when called. Why it matters. The server is plain code, not the AI, and connected does not mean safe: some tools write, delete or send. How. Keep write tools on the ask list in your permission rules (they are named mcp__server__tool), and use a read-only database user for database servers.

Covered on Day 7.

Q15 How much of a skill does Claude hold in context before the skill is used?

  1. Every file in the skill folder
  2. Nothing at all
  3. Only its one-line description
  4. The whole SKILL.md of every skill
Show the answer

Answer: C. Only its one-line description

What. A skill is a folder with a SKILL.md: a short header plus Markdown instructions. Why. Only the description is listed until the skill is used, so you can keep many skills for almost no context. That is also why the description matters most: if it does not match how you ask, the skill never loads. How. Check what is loaded with /skills in the terminal, or type / in the VS Code panel.

Covered on Day 8.

Q16 You wrote a deploy skill. How do you stop Claude from running it on its own when you say "ship it" in passing?

  1. Make the description longer
  2. Nothing, it can only run when you type it
  3. Rename the folder
  4. Add disable-model-invocation: true to the header
Show the answer

Answer: D. Add disable-model-invocation: true to the header

What. By default both you and Claude can run a skill. Why. Anything with side effects, such as deploys, pushes and messages, should only fire when you decide. How. Add disable-model-invocation: true to the SKILL.md header. Rule of thumb: if running it twice by accident would hurt, gate it.

Covered on Day 8.

Q17 What is the main reason to hand a big, noisy job to a subagent?

  1. It skips permissions
  2. It works in its own fresh context, and only a short result comes back to your main chat
  3. It is free
  4. It makes Claude smarter
Show the answer

Answer: B. It works in its own fresh context, and only a short result comes back to your main chat

What. A subagent is a separate Claude with its own context window, tools and optionally its own model. Why. The files it read and the dead ends it explored never fill your main context (Day 5). You can also limit what it may do, for example a read-only reviewer. How. Ask for one in plain words ("use an Explore agent to find where login errors are handled") or create .claude/agents/name.md.

Covered on Day 9.

Q18 You want a rule that Claude can never edit .env, with no exceptions. Which tool fits best?

  1. A PreToolUse hook that exits with code 2
  2. A sentence in CLAUDE.md
  3. A Notification hook
  4. A PostToolUse hook
Show the answer

Answer: A. A PreToolUse hook that exits with code 2

What. A hook is your command, run by Claude Code at a fixed moment. PreToolUse runs before the tool and can block it: exit code 2 blocks, and what you write to stderr goes back to Claude as the reason. Why. PostToolUse runs after the action, so it can react but cannot undo it. How. Define it in settings under hooks with a matcher such as Edit|Write, then check it with /hooks.

Covered on Day 9.

Q19 Where does a plugin's manifest go, and what else may sit in that folder?

  1. In .claude-plugin/, together with skills/ and agents/
  2. In .claude-plugin/plugin.json, and only that file belongs in .claude-plugin
  3. In the root, next to skills/
  4. In ~/.claude/plugin.json
Show the answer

Answer: B. In .claude-plugin/plugin.json, and only that file belongs in .claude-plugin

What. A plugin bundles skills, subagents, hooks and MCP servers behind one manifest. Why. The classic mistake is putting skills/, agents/ or hooks/ inside .claude-plugin/; they sit at the plugin root instead. How. Test locally with claude --plugin-dir ./my-plugin and read the Errors tab in /plugin if something does not load.

Covered on Day 10.

05Operate: Days 11 and 12

Scripts, automation, models, cost and parallel work. 6 questions.

Q20 What does claude -p "..." do?

  1. Prints the version
  2. Opens plan mode
  3. Pauses the session
  4. Runs one prompt, prints the answer and stops, with no back and forth
Show the answer

Answer: D. Runs one prompt, prints the answer and stops, with no back and forth

What. -p (short for --print) is headless mode. Why. It lets scripts and CI call Claude Code like any other command, and you can pipe data in and read JSON out with --output-format json. How. Works in any terminal, including VS Code's integrated one: git diff main | claude -p "list any typos".

Covered on Day 11.

Q21 In a headless run, Claude wants a command you did not allow. What happens?

  1. It is denied, because nobody is there to approve it
  2. It runs anyway
  3. The run crashes
  4. It asks you at the keyboard
Show the answer

Answer: A. It is denied, because nobody is there to approve it

What. Headless runs start in the normal permission mode, and anything that would prompt is simply denied. Why. Every tool you allow is something a robot can do at 3 a.m., so start with the smallest list that finishes the job. How. Grant tools up front with --allowedTools "Read,Edit" or a mode like --permission-mode dontAsk for locked-down CI.

Covered on Day 11.

Q22 Who can trigger the @claude GitHub Action on an issue or pull request?

  1. Only Anthropic
  2. Only people with write access to the repository (and bots only if you list them)
  3. Only the repository's bots
  4. Anyone on the internet
Show the answer

Answer: B. Only people with write access to the repository (and bots only if you list them)

What. The Action checks the commenter before it starts. Why. Otherwise a stranger could spend your API money from a public issue. How. Set it up with /install-github-app inside Claude Code (or the manual steps on Day 11), keep keys in repository secrets, and put your standards in CLAUDE.md.

Covered on Day 11.

Q23 What does the opusplan model alias do?

  1. Uses Opus for every step
  2. Turns plan mode off
  3. Uses Opus while planning, then Sonnet when it starts executing
  4. Uses Haiku to plan and Opus to build
Show the answer

Answer: C. Uses Opus while planning, then Sonnet when it starts executing

What. A hybrid alias. Why. The hard decision happens in the plan, which uses few tokens; most tokens go into reading files and writing edits. Put the expensive model on the decision and the cheaper one on the typing. How. /model opusplan in a session, or click the model name under the VS Code prompt box. Aliases such as sonnet and opus always mean the latest of that kind.

Covered on Day 12.

Q24 Which command makes a second, isolated session on its own branch, so two sessions cannot collide?

  1. claude --clone
  2. claude --worktree fix-rounding
  3. claude --copy fix-rounding
  4. claude -p fix-rounding
Show the answer

Answer: B. claude --worktree fix-rounding

What. A git worktree is a second folder with its own files on its own branch, sharing the same history. Why. Two sessions in one folder edit each other's files. How. claude -w name creates .claude/worktrees/name/ on a branch called worktree-name. The repo needs at least one commit, and add .claude/worktrees/ to .gitignore. List them with git worktree list.

Covered on Day 12.

Q25 Three parallel sessions will usually use...

  1. At least three sessions' worth of tokens, because each reloads the project context
  2. Fewer tokens, because they share a cache
  3. The same tokens as one session
  4. No tokens in the background
Show the answer

Answer: A. At least three sessions' worth of tokens, because each reloads the project context

What. Parallel sessions save your waiting time, not tokens. Why. Each session carries its own context, and merge conflicts erase the time you saved if the sessions touch the same files. How. Run only as many as you can review carefully (two or three is plenty), give each its own worktree, and check the spend with /usage.
