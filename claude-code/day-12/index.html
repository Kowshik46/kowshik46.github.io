Nothing new to learn: the point is to see when to reach for each tool.

01The big picture: tools are easy, the order is the skill

What. Ten days gave you ten tools. This article is one continuous walkthrough that uses them in the order a real project needs them. We build a tiny app called billsplit, a command that splits a restaurant bill between friends, tip included, without losing a single cent.

Why it matters. Reading about a hammer, a saw and a level does not teach you to build a shelf. Beginners often know every feature and still do not know what to do first. The answer is the same on almost every project: write down the rules, plan before you build, build in small steps with tests, save your work, then slowly add automation for whatever annoyed you along the way.

How this article is organised. Ten stages, each one maps to a day, and each says what you do, why you do it at that moment, and how, in the terminal and in VS Code.

02What we are building, and what you need

What. billsplit is a small Python command: python -m billsplit 100 3 --tip 10 prints what each of three people owes for a 100 bill with a 10 percent tip. The interesting part is money maths: 110.00 split three ways is 36.666..., and real shares must add back up to exactly 110.00. That detail is a classic bug, which makes it a good thing for Claude to plan, test and review.

Why this project. It is small enough to finish in one sitting, has a real edge case (leftover cents), and is easy to test. The same steps work for a website, an API or a script. Swap in your own idea if you prefer.

You need:

Claude CodeInstalled and signed in. If not, do Day 3 first (terminal or VS Code extension).
Python 3.9+Check with python --version (on macOS and Linux, python3 --version).
Git and a GitHub accountCheck with git --version. A free account is enough.
VS Code (optional)Every stage also says what to click. The terminal parts also run in the VS Code integrated terminal, Ctrl+`.

03Stage 1: Set up the folder (Day 3)

What and why. Claude Code works inside a folder. It reads the files there and its changes land there. Starting from a clean, git-tracked folder means every change Claude makes is something you can see and undo. How:

>_PowerShell
—☐✕
PS C:\dev> mkdir billsplit
PS C:\dev> cd billsplit
PS C:\dev\billsplit> git init
PS C:\dev\billsplit> python -m venv .venv
PS C:\dev\billsplit> .\.venv\Scripts\Activate.ps1
PS C:\dev\billsplit> pip install pytest
PS C:\dev\billsplit> claude

On macOS and Linux use source .venv/bin/activate in place of the activate line. If PowerShell refuses to run the activate script, run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once.

In VS Code: use File, Open Folder and choose billsplit, open the integrated terminal with Ctrl+` for the commands above (skip the last claude line), then open the Claude Code panel from the Spark icon in the top right of the editor. It works on the folder you have open.

Add one file before you move on so the virtual environment never reaches git: create .gitignore containing the two lines .venv/ and __pycache__/.

04Stage 2: Write down the rules (Day 2)

What. A CLAUDE file (CLAUDE.md) is a plain text file in your project that Claude reads at the start of every session. Why now. It is the cheapest thing you will do all day and it pays back on every prompt after it. Claude forgets everything between sessions, so anything you do not write down you will explain again tomorrow. How: ask Claude to draft it, then trim it.

>_PowerShell — in a Claude Code session
—☐✕
> /init

On an empty project /init has little to find, so replace what it wrote with the few things only you know. Keep it short. Here is the whole file for billsplit:

>_CLAUDE.md
—☐✕
# billsplit

A command-line tool that splits a restaurant bill between people.

## Rules
- Python 3.9+, standard library only. The only extra is pytest for tests.
- Money is ALWAYS whole cents (integers). Never use float for stored amounts.
- Shares must add up to exactly the total plus tip. No cent is lost.
- Code lives in billsplit/, tests in tests/.

## Commands
- Run the app: python -m billsplit 100 3 --tip 10
- Run tests: python -m pytest -q

## Working agreement
- Write or update a test for every behaviour change.
- Keep functions small. Do not add dependencies without asking.

Check it worked: run /memory in the session and you should see the file listed as loaded. In VS Code the same /init works in the panel's prompt box. Remember the Day 2 rule: say what Claude cannot guess (rules, commands), not what it can read from the code.

05Stage 3: Plan before you build (Day 4)

What. Plan mode lets Claude read and think but not change anything. It writes a plan, you read it, and only then does it start editing. Why now. A wrong idea costs seconds to fix in a plan and minutes to undo in code. For a feature with a hidden trap (our leftover cents), a plan is where that trap shows up. How: press Shift+Tab until the status bar says plan mode (in VS Code, use the mode picker at the bottom of the prompt box, or start from the shell with claude --permission-mode plan). Then give a clear ask:

>_PowerShell — plan mode
—☐✕
> Plan billsplit as described in CLAUDE.md. Behaviour: total, number of
  people and optional tip percent in, each person's share out, in cents.
  List the edge cases (rounding, zero people, negative numbers), the files you
  would create and the tests you would write. Do not write code yet.

Read the plan like a reviewer. Does it name the leftover-cents problem? Does it use integers? If something is off, answer in plain words (use whole cents, not floats) and let it revise. When the plan is right, approve it. In the terminal the approval prompt offers to start building, and in VS Code you press the approve button on the plan. That is the whole Day 4 habit: explore, plan, then build.

06Stage 4: Set the guardrails and keep context clean (Day 5)

What and why. Two things stop a long session from going wrong. Permissions decide what Claude may do without asking, so you are not clicking "yes" on every test run, and so secrets stay out of reach. Context is Claude's working memory: the fuller it is with old, unrelated chat, the worse it performs. How: create .claude/settings.json (VS Code: New File in the Explorer) with this:

>_.claude/settings.json
—☐✕
{
  "permissions": {
    "allow": [
      "Bash(python -m pytest *)",
      "Bash(python -m billsplit *)",
      "Bash(git status *)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "deny": [ "Read(./.env)", "Read(./.env.*)" ]
  }
}

The allow list is safe on purpose: it runs the tests and the app and reads git state, nothing that writes or deletes. The deny list blocks reading secret files even if a prompt asks. You can edit rules any time with /permissions. For context, build two habits: run /context now and then to see how full the window is, and run /clear when you finish a task and start another. Rules in the CLAUDE file survive a /clear, because they reload.

07Stage 5: Build in small steps, with tests (Days 4 and 5)

What. Instead of one giant request, you ask for one small thing, check it, then ask for the next. Why. Small steps are easy to review, easy to undo, and keep the context focused. Tests give Claude (and you) a way to prove each step works instead of hoping. How: switch out of plan mode (Shift+Tab to accept-edits or default) and run these prompts one at a time:

>_PowerShell — step by step
—☐✕
# step 1: tests first, so "done" has a definition
> Create tests/test_core.py with tests for a split_bill(total_cents,
  people, tip_percent=0) function: an even split, leftover cents never lost,
  tip added, and zero people raising ValueError. Run them and show they fail.

# step 2: the function
> Now write billsplit/core.py so those tests pass. Run the tests.

# step 3: the command line
> Add billsplit/__main__.py using argparse so
  "python -m billsplit 100 3 --tip 10" prints one line per person.

The heart of the result looks like this. Notice the divmod line: it hands the leftover cents to the first people, which is exactly the trap the plan warned about.

>_billsplit/core.py
—☐✕
def split_bill(total_cents, people, tip_percent=0):
    """Return cents owed per person. Shares sum to total plus tip."""
    if people < 1:
        raise ValueError("people must be at least 1")
    if total_cents < 0 or tip_percent < 0:
        raise ValueError("total and tip cannot be negative")
    grand = round(total_cents * (100 + tip_percent) / 100)
    base, extra = divmod(grand, people)
    return [base + 1 if i < extra else base for i in range(people)]

Run python -m pytest -q and then python -m billsplit 100 3 --tip 10. You should see Person 1: 36.67, Person 2: 36.67, Person 3: 36.66, which adds up to exactly 110.00. In VS Code, Claude's edits show as diffs in the editor: accept or reject each one, and open the Testing panel if you want a green tick view. If a step goes wrong, Esc Esc (or the rewind button in VS Code) takes you back to before it.

08Stage 6: Save and share your work (Day 6)

What and why. Git is your safety net and your history. A good commit is one finished idea with a clear message, and a pull request is how others review it. Do this as soon as the first step works, not at the end of the day. How: make a branch, ask for a commit, push, and open a pull request.

>_PowerShell — git with Claude
—☐✕
> Create a branch called feature/split-core, and commit what we have
  with a clear message. Do not add the .venv folder.

# first push needs a GitHub repo. Create an empty one named billsplit, then:
> Add the GitHub repo https://github.com/YOUR-NAME/billsplit as origin
  and push the branch.

> Open a pull request for this branch. Explain what changed and how to test it.

Opening a pull request from Claude needs the GitHub CLI (gh auth login once) or the GitHub connection from Stage 7. Always read the diff before you accept a commit: run /diff or git diff. Never let a commit contain secrets or the virtual environment folder. If you would rather not use the command line for git, VS Code's Source Control panel does the same steps with buttons.

09Stage 7: Let Claude read your GitHub issues (Day 7)

What. MCP (Model Context Protocol) is the standard plug that lets Claude use outside tools. The GitHub server lets it read issues and pull requests directly instead of you pasting text in. Why now. Your project now lives on GitHub, so the next feature request is probably an issue there. How: create a GitHub fine-grained token with read access to this one repository, then:

>_PowerShell
—☐✕
claude mcp add --transport http github https://api.githubcopilot.com/mcp/ --header "Authorization: Bearer YOUR_GITHUB_PAT"
claude mcp list

Inside Claude Code, /mcp should show github as Connected. Then try: read issue 1 on my billsplit repo and propose a plan. Keep the token read-only and scoped to one repo, never paste it into a file you commit, and leave write actions on the ask list (Day 7). In VS Code, run the same claude mcp add in the integrated terminal and check the result with /mcp in the panel. Open the repo and file an issue first, such as "add a --round-up option", so Claude has something real to read.

10Stage 8: Turn a repeated check into a skill (Day 8)

What. A skill is a folder with a SKILL.md file: instructions Claude loads when needed and that you can also run as a slash command. Why now. By now you have typed "run the tests, then try the app with three sample bills" more than once. Anything you type twice belongs in a skill. How: create .claude/skills/check-split/SKILL.md:

>_.claude/skills/check-split/SKILL.md
—☐✕
---
name: check-split
description: Run the tests and try billsplit on sample bills to prove the shares add up
disable-model-invocation: true
---

1. Run python -m pytest -q and report the result.
2. Run python -m billsplit for these bills and check the shares add up
   to total plus tip each time:
   - 100 with 3 people, no tip
   - 100 with 3 people, 10 percent tip
   - 0.01 with 2 people
3. Finish with PASS or FAIL and one line on why.

Now /check-split runs the same careful check every time, from the terminal or the VS Code panel. Because of disable-model-invocation: true it only runs when you type it, which is right for something that executes commands.

11Stage 9: Add a reviewer and a safety net (Day 9)

What and why. Two pieces here. A subagent is a helper with its own fresh context and limited tools: a reviewer that reads your diff without the bias of having written it. A hook is a rule that runs automatically on an event, so it cannot be forgotten: here, run the tests after every Python file Claude edits. How: the reviewer is one file, .claude/agents/code-reviewer.md:

>_.claude/agents/code-reviewer.md
—☐✕
---
name: code-reviewer
description: Reviews code changes for bugs, money-rounding mistakes and missing tests.
tools: Read, Grep, Glob, Bash
model: sonnet
---

You are a careful reviewer. Run git diff and review only the changed code.
Pay special attention to money handling: floats, rounding and lost cents.
Report must fix, should fix and nice to have, each with file, line and fix.
Never edit files.

Use it by asking use the code-reviewer agent on my changes. For the safety net, add a small script and a hook. The script reads the event from stdin, ignores anything that is not a Python file, runs the tests, and exits with code 2 on failure so Claude is told and fixes it:

>_.claude/hooks/run_tests.py
—☐✕
import json, subprocess, sys

event = json.load(sys.stdin)
path = event.get("tool_input", {}).get("file_path", "")
if not path.endswith(".py"):
    sys.exit(0)

result = subprocess.run([sys.executable, "-m", "pytest", "-q", "-x"],
                        capture_output=True, text=True)
if result.returncode != 0:
    print(result.stdout[-1500:], file=sys.stderr)
    sys.exit(2)
sys.exit(0)

Then register it by adding a hooks block next to permissions in .claude/settings.json:

>_.claude/settings.json (add this)
—☐✕
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "python .claude/hooks/run_tests.py" }
        ]
      }
    ]
  }

Type /hooks to confirm it is listed under PostToolUse. On macOS and Linux write python3 if python is not found. Test it by asking Claude to change the rounding in a way that breaks a test: the hook feeds the failure back and Claude repairs its own mistake. Remember the Day 9 warning: a hook runs with your permissions, so only keep hooks you understand.

12Stage 10: Package the setup as a plugin (Day 10)

What and why. Right now the skill, reviewer and hook live in this one project. A plugin turns them into one installable unit, so your next project, or a teammate, gets all three with one command. How: create a folder next to the project and copy the pieces in.

>_billsplit-kit
—☐✕
billsplit-kit\
  .claude-plugin\plugin.json
  skills\check-split\SKILL.md
  agents\code-reviewer.md
  hooks\hooks.json
  scripts\run_tests.py
>_.claude-plugin/plugin.json and hooks/hooks.json
—☐✕
{
  "name": "billsplit-kit",
  "description": "Check skill, money-aware reviewer and a test-after-edit hook",
  "version": "1.0.0"
}

// hooks/hooks.json: same shape as your settings, new script path
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command",
            "command": "python \"${CLAUDE_PLUGIN_ROOT}/scripts/run_tests.py\"" }
        ]
      }
    ]
  }
}

Validate and try it, from a shell in a fresh project:

>_PowerShell — validate and load
—☐✕
claude plugin validate .\billsplit-kit
claude --plugin-dir .\billsplit-kit

> /billsplit-kit:check-split
> use the billsplit-kit:code-reviewer agent on my changes

Watch out for duplicates. Once the plugin works, remove the originals from .claude/ (especially the hook), otherwise the hook fires twice. To share it, put the folder in a Git repo with a marketplace file as in Day 10 and your team installs it with /plugin marketplace add and /plugin install.

13The loop you will use every day

What and why. After one run through, the stages collapse into a short loop. This is the habit worth keeping, because it works on any project size. How:

RulesIs the CLAUDE file current? Add any rule you had to repeat.
PlanNew feature or risky change: plan mode first.
BuildTests, then code, in small steps. /clear between tasks.
Check/check-split style skill, plus the reviewer subagent.
SaveCommit small, open a pull request, read the diff.
AutomateAnnoyed twice? Make it a skill, a hook or an agent.

The last step is what turns Claude Code from a chatbot into your setup: every irritation becomes a file, and the plugin is how those files travel.

14Which tool for which problem

"It keeps forgetting our rules"CLAUDE file (Day 2).
"It built the wrong thing"Plan mode and clearer prompts (Day 4).
"It got slow and confused"/context, /compact or /clear (Day 5).
"It keeps asking permission"Allow rules in settings (Day 5).
"I need to undo or share"Git and pull requests (Day 6).
"It needs data from another tool"An MCP server (Day 7).
"I keep typing the same instructions"A skill (Day 8).
"I want a second opinion"A subagent (Day 9).
"This must happen every time"A hook (Day 9).
"My teammate needs all of it"A plugin (Day 10).

15When something goes wrong

Claude does not follow the CLAUDE fileRun /memory to confirm it loaded, and shorten it. Long files get ignored.
The hook never firesRun /hooks. Check the event is PostToolUse, the matcher is Edit|Write and the script path is right.
Tests pass in the terminal, fail in the hookThe hook may run with a different Python. Use the venv's Python path in the command, for example .venv\Scripts\python.
MCP shows FailedToken expired or wrong scope. Re-add the server with a new token and run /mcp.
Skill or agent not foundCheck the folder name matches name:, restart the session if you created .claude/skills just now.
Plugin loads but hooks run twiceThe same hook is still in .claude/settings.json. Delete the original.
Git push rejectedThe remote already has commits. Ask Claude to fetch and rebase, and read the result before pushing.

17Questions beginners ask

Do I need all ten stages for every project?No. A tiny script needs a CLAUDE file, git and a test. Add the rest when a real annoyance shows up. Stages 8 to 10 are for things you repeat.
Why write tests before code?They define "done". Claude can run them and fix itself, so you review results instead of guessing.
Can I use another language?Yes. Change the commands in the CLAUDE file, the allow rules and the hook script. The stages stay the same.
Is the GitHub token safe to give Claude?Use a fine-grained token limited to one repository and read-only permissions, and revoke it when you stop. Never commit it.
Can I do this entirely in VS Code?Almost. The panel handles prompts, plan mode, /init, /mcp, /hooks and /plugins. The terminal is only needed for commands like claude mcp add and claude plugin validate, and VS Code has one built in.
What if I get stuck halfway?Stop at any stage. Each one leaves the project working and committed, so you can pick up the next day.
