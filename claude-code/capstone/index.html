Features do not build projects, order does. Write the rules, plan, test, build, then automate only what actually annoyed you.

01The big picture: why order matters

What. A capstone is one project that uses everything you learned, in sequence. Ours is a command-line bill splitter: python -m billsplit 100 3 --tip 10 splits 100.00 between 3 people with a 10% tip and prints what each person pays.

Why a bill splitter. It is small enough to finish in one sitting and it hides a real trap. 110.00 divided by 3 is 36.666..., so you cannot just round each share: three shares of 36.67 add up to 110.01, a cent that does not exist. A good tool hands the extra cents out one at a time, so the total is exactly right. A trap like this is what plan mode and tests are for.

The ten stages.

1. Set up the folderAn empty git repository and a place to run code. Day 6.
2. Write the rules/init and a short CLAUDE.md. Days 3 and 5.
3. Plan before codePlan mode finds the cents trap before any code exists. Day 4.
4. Tests firstSmall tests that define "correct". Day 4.
5. Build to greenClaude writes code until the tests pass. Days 4 and 5.
6. Make it a commandA tiny command-line wrapper you can run.
7. Commit and open a pull requestClaude reads the GitHub issue through MCP. Days 6 and 7.
8. Skill: check-splitA repeatable check you invoke by name. Day 8.
9. Subagent and hookA reviewer in a fresh context, and tests that rerun after every edit. Day 9.
10. Package as a pluginOne folder that sets up your next project. Day 10.

Terminal or VS Code. Every stage works in both. In the terminal you type the prompts shown here into claude. In VS Code open the Claude panel (the spark icon, or Ctrl+Esc) in the folder and type the same prompts. Slash commands such as /init and /mcp work in the panel too, and plan mode is the mode selector at the bottom of the prompt box. Shell commands (git, python) go in the integrated terminal, Ctrl+`.

03Stage 1: set up the folder

What and why. Git first, before any code. Day 6 showed why: a repository gives Claude's edits a safety net you can step back from. How:

>_PowerShell: an empty project
—☐✕
mkdir billsplit
cd billsplit
git init
python -m venv .venv
.venv\Scripts\Activate.ps1      # on macOS or Linux: source .venv/bin/activate
pip install pytest
code .                          # VS Code, optional

Checkpoint. git status works and pytest --version prints a version. Add a .gitignore with .venv/ and __pycache__/ so the virtual environment never gets committed.

04Stage 2: write the rules

What. CLAUDE.md is the file Claude reads at the start of every session (Days 3 and 5). Why now. Rules written before the first line of code mean you never have to repeat yourself. How: start claude in the folder and run /init. On an empty folder it has little to scan, so then replace the draft with a short file of your own:

>_CLAUDE.md
—☐✕
# billsplit
A command-line bill splitter in Python.

## Rules
- Money is stored as integer cents, never floats.
- Shares must add up to the total exactly. Leftover cents go to the first people.
- Every function gets a test in tests/. Run: python -m pytest -q
- Keep it in one package, billsplit/, standard library only.

## Commands
- Run: python -m billsplit 100 3 --tip 10
- Test: python -m pytest -q

Checkpoint. Run /memory and confirm the file is loaded. Keep it short: a long CLAUDE.md costs tokens on every message (Day 12). Commit it: git add -A; git commit -m "Add rules".

05Stage 3: plan before code

What. Plan mode (Day 4) lets Claude read and think but not edit until you approve. Why. The leftover-cents trap is cheap to fix in a plan and annoying to fix in finished code. How: press Shift+Tab until the mode reads plan (in VS Code, pick Plan in the mode selector), then ask:

>_Prompt in plan mode
—☐✕
Plan a bill splitter: billsplit.split(total_cents, people, tip_percent).
Shares must add up exactly, e.g. 100.00 split 3 ways with a 10% tip.
List the edge cases first, then the files, then the tests.

Read the plan. A good one names the trap itself: "11000 cents divided by 3 is 3666 remainder 2, so two people pay 3667 and one pays 3666". If it does not mention it, say so and ask it to revise. When you are happy, approve it. Checkpoint: you can explain the plan in one sentence.

06Stage 4: tests first

What and why. A test is a few lines that say what correct looks like. Writing them before the code gives Claude a target it cannot talk its way around. How: ask Claude to write the tests only, then run them and watch them fail.

>_tests/test_split.py
—☐✕
from billsplit.core import split

def test_even_split():
    assert split(9000, 3, 0) == [3000, 3000, 3000]

def test_leftover_cents_go_to_first_people():
    assert split(10000, 3, 10) == [3667, 3667, 3666]

def test_shares_always_add_up():
    for people in range(1, 12):
        assert sum(split(10001, people, 15)) == round(10001 * 1.15)

def test_rejects_zero_people():
    import pytest
    with pytest.raises(ValueError):
        split(1000, 0, 0)

Checkpoint. python -m pytest -q fails with an import error. That is correct: the code does not exist yet. A test that cannot fail proves nothing, so seeing red first matters. Commit the tests.

07Stage 5: build until green

What. Switch back to normal mode and tell Claude to make the tests pass. Why. You are the reviewer; the tests are your proof. How:

>_Prompt
—☐✕
Implement billsplit/core.py so every test in tests/ passes. Run the tests after each change and stop when they are green.
>_billsplit/core.py (roughly what you should get)
—☐✕
def split(total_cents, people, tip_percent):
    if people < 1:
        raise ValueError("people must be at least 1")
    total = round(total_cents * (100 + tip_percent) / 100)
    base, extra = divmod(total, people)
    return [base + 1 if i < extra else base for i in range(people)]

Read it. divmod(11000, 3) gives 3666 and 2, so the first two people get one extra cent each. Your version may look different; judge it by whether the tests pass and you can follow it. Checkpoint: green tests, then git commit.

08Stage 6: make it a command

What and why. Code you can only call from tests is not a tool yet. How: ask Claude for a small wrapper using the standard library, with a test for it.

>_Prompt
—☐✕
Add billsplit/__main__.py using argparse: positional total (in dollars) and people, optional --tip percent. Convert to cents, call split, print each share like 36.67. Add a test.
>_PowerShell: try it
—☐✕
python -m billsplit 100 3 --tip 10
# 36.67
# 36.67
# 36.66

Checkpoint. Three lines that add to 110.00. Commit.

09Stage 7: commit and open a pull request

What. Push the work to GitHub and open a pull request (Day 6). Why with MCP. If you have connected the GitHub MCP server (Day 7), Claude can read the issue that started the work and write a pull request that references it, instead of you copying text around. How: create a repository, add an issue such as "Split a bill with tip, no lost cents", then:

>_PowerShell
—☐✕
git switch -c split-with-tip
git remote add origin https://github.com/YOUR-NAME/billsplit.git
git push -u origin split-with-tip
# then inside claude:
Read issue #1 and open a pull request that closes it. Summarise what changed and how I can verify it.

No MCP server connected? Run /mcp to see what you have, or just ask Claude to draft the title and description and paste them yourself. Checkpoint: a pull request with a clear description exists. Read the diff before you merge; Claude wrote it, you own it.

10Stage 8: automate the check as a skill

What and why. By now you have typed "run the tests and confirm 100 split 3 ways with a tip is 110.00" more than once. That annoyance is the signal to make a skill (Day 8). Automate what annoyed you, not what you imagine might. How:

>_.claude/skills/check-split/SKILL.md
—☐✕
---
name: check-split
description: Run the billsplit tests and verify the 100 / 3 / 10 percent example adds up to 110.00. Use before committing changes to the splitting logic.
---
1. Run python -m pytest -q and report failures.
2. Run python -m billsplit 100 3 --tip 10.
3. Confirm the three lines add up to exactly 110.00.
4. Reply with PASS or FAIL and one line why.

Invoke it with /check-split. Checkpoint: it reports PASS.

11Stage 9: a reviewer subagent and a hook

What and why. Two small automations from Day 9. A subagent reviews with a fresh context, so it is not biased by the conversation that wrote the code. A hook runs a command automatically, so tests rerun after every edit and you stop forgetting. How:

>_.claude/agents/reviewer.md
—☐✕
---
name: reviewer
description: Reviews billsplit changes for rounding bugs and missing tests. Use after finishing a change.
tools: Read, Grep, Glob
model: haiku
---
You are a strict reviewer. Check money handling uses integer cents, shares add up exactly, and every function has a test. Report problems as a short list. Do not edit files.
>_.claude/settings.json
—☐✕
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "python -m pytest -q" }]
      }
    ]
  }
}

Ask "use the reviewer subagent on my last change". Then make any small edit and watch the tests run on their own. Checkpoint: you saw a test run you did not ask for. Note the trade-off below: a hook that runs on every edit can be slow or noisy.

When this stage is not worth it

  • If your tests take more than a few seconds, a hook after every edit slows every turn. Run it on Stop instead, or skip it.
  • A reviewer subagent costs tokens. For a 50-line change you read yourself, it adds little.
  • Do not automate something you have done once. Wait until it has annoyed you twice.

12Stage 10: package it as a plugin

What and why. Your skill, subagent and hook now live in one project. A plugin (Day 10) bundles them so your next project starts fully set up. How: make a folder with a manifest and move the pieces in.

>_Plugin layout
—☐✕
billsplit-kit/
  .claude-plugin/
    plugin.json
  skills/check-split/SKILL.md
  agents/reviewer.md
  hooks/hooks.json
>_billsplit-kit/.claude-plugin/plugin.json
—☐✕
{
  "name": "billsplit-kit",
  "description": "Check, review and test hooks for the bill splitter",
  "version": "0.1.0"
}
>_PowerShell: try it without installing
—☐✕
claude --plugin-dir ./billsplit-kit
# inside the session:
/billsplit-kit:check-split

Plugin skills are namespaced with the plugin name, which is why the command is /billsplit-kit:check-split. The hook file uses the same JSON shape as stage 9 under a top-level "hooks" key. Checkpoint: the namespaced skill runs and reports PASS. Share it later through a marketplace (Day 10) once it is stable.

13What you just did

Look back at the order: rules, plan, tests, code, pull request, skill, subagent and hook, plugin. Each step made the next one safer. Rules and the plan kept the work on track. Tests let you trust the code without reading every line. Automation came last because it only pays off for things you have already felt as friction.

14When it does not work

Plan mode lets me editYou are not in plan mode. Press Shift+Tab until the mode shows plan, or pick it in the VS Code mode selector.
Claude "fixes" a test instead of the codeTell it the tests are the specification and must not change. Review the diff; if a test file changed, ask why.
The hook never firesCheck the JSON is valid, the matcher is Edit|Write, and run /hooks to see what loaded. Settings are read at session start, so restart after editing.
The skill is not foundThe folder name and the name: field must match, and the file must be called SKILL.md in capital letters.
The plugin skill is not foundUse the namespaced form /billsplit-kit:check-split and make sure you started Claude with --plugin-dir.
MCP says FailedRun /mcp, pick the server and finish the sign-in. claude mcp get with the name prints the reason (Day 7).

15Going further: where to go from here

You have now used the core of Claude Code on a real project. The roadmap had a "Going further" row; here it is. Pick what matches your work rather than trying everything.

Use it on your own codeThe best next step is not reading more. Take one real task this week through the same order: rules, plan, tests, build. Day 4 and this page are your checklist.
Tune it to your habitsRun /insights (Day 12) after a few sessions, read where friction showed up, and fix one thing in CLAUDE.md, one skill or one hook.
Run it unattendedScripts, claude -p and GitHub Actions (Day 11) let it review pull requests and run scheduled jobs. Start with read-only tasks and a budget cap.
Run work in parallelGit worktrees and several sessions (Day 12) when you have independent tasks. Two or three is plenty.
Build on the SDKWhen you want Claude Code's loop inside your own program, the Agent SDK exposes the same engine. Start from the official overview and the headless docs.
Share what you buildPublish a skill or a plugin (Days 8 and 10). Writing it up for someone else is the fastest way to find the gaps in your own understanding.

How to keep current. This tool changes fast. Run claude update now and then, skim the official changelog for your version, and treat commands in any tutorial, this one included, as a starting point to verify with claude --version and the docs. 17Questions beginners ask

Do I have to use Python?No. The order of stages is the lesson. Swap pytest for your language's test runner.
Do I need the GitHub MCP server?No. It saves copy-pasting in stage 7. Without it, ask Claude to draft the pull request text.
Should every project get all ten stages?No. A one-off script needs stages 1 to 5 at most. Skills, hooks and plugins are for work you repeat.
What if the plan is wrong?Say so and ask for a revision before approving. Rejecting a plan costs almost nothing; rejecting finished code does not.
Is the series finished?The daily articles are. All twelve days, the capstone and the Claude Quiz stay up, and I update the "Last verified" dates when I recheck them.
